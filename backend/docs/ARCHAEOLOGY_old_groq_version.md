## Verdict

Same overall shape, diverged in the internals. The big architectural bets from your two diagrams — offline indexing / online query split, hybrid dense+sparse retrieval, Kannada-first design, rerank-before-generate — all survived into the build. But almost every "smart" component in the middle was swapped for a simpler or different implementation, usually without being written down as a decision. That's the core problem: not that the substitutions are all bad (some are genuine upgrades), but that nothing documents *why* they happened, so right now it reads as drift rather than engineering trade-offs.

## What the app does, plainly

A farmer types a sugarcane question in Kannada into a Next.js chat page. FastAPI routes it: a Groq-hosted LLM call classifies the query type and produces an English keyword version. The query is embedded with BGE-M3 (dense + lexical/sparse), searched against a Qdrant collection of chunked sugarcane knowledge, fused and boosted into a top-5 set, each chunk individually vetted by another LLM call, then — for price questions or if nothing relevant was found — supplemented with a live Tavily web search. The surviving context is stuffed into a strict "answer only from this context" Kannada prompt, generated by Llama-3.1-8b-instant, saved to MongoDB with the running chat history, and returned with two scores (retrieval confidence, LLM-judged faithfulness) that the frontend currently discards.

## Target workflow — the reconciled, complete version

This keeps everything that's working, restores the two planned techniques that were quietly dropped where they add real value, and fixes the two techniques that were replaced with something worse.

### Part 1 — Offline indexing (batch, runs once per data update)

| Step | What it does | Tech |
|---|---|---|
| 1. Collect | Gather sugarcane-specific agricultural content from the research papers your mentor shared + any Karnataka govt. sources | Manual curation, tracked in repo (not gitignored) with a short provenance note per source |
| 2. Normalize | Unicode NFC normalization, whitespace/punctuation cleanup | `indic-nlp-library` |
| 3. Segment (ablation, not mandatory) | Try explicit root+suffix splitting; measure whether it actually improves retrieval over BGE-M3's own subword tokenizer | `Morfessor` — run as an A/B, keep only if it measurably helps |
| 4. Chunk | Token-aware, boundary-respecting splitting (~300 tokens, overlap) | `RecursiveCharacterTextSplitter` (LangChain, or a small custom token-based version) |
| 5. Embed | Dense 1024-dim vector + native lexical/sparse weights per chunk | `BGE-M3` (`FlagEmbedding`) |
| 6. Index | Persist dense + sparse vectors and metadata (category, source doc) | `Qdrant` (keep — already working, better hybrid support than the originally planned Chroma) |

### Part 2 — Online query (every request)

| Step | What it does | Tech |
|---|---|---|
| 1. Input | Farmer types (voice is a stretch goal, not required now) | Next.js chat UI |
| 2. Preprocess | Same normalization/segmentation pipeline as indexing, so query and corpus live in the same space | Same as above |
| 3. Embed query | Dense + sparse vectors | `BGE-M3` |
| 4. Hybrid retrieve | Top-15-20 candidates each from dense and sparse search | `Qdrant` |
| 5. Fuse | Combine the two ranked lists **without** score normalization | **Reciprocal Rank Fusion** — replaces the current weighted-sum + ×2 heuristic |
| 6. Rerank | Score the fused candidates for actual relevance, keep top-3-5 | **Cross-encoder** (`bge-reranker-v2-m3`, local, CPU-friendly) — replaces the current per-chunk LLM yes/no vote |
| 7. Web fallback | Only if retrieval confidence is still low, or query is price-related | `Tavily` (keep, it's already sensible) |
| 8. Generate | Strict context-grounded Kannada answer | `Llama-3.1-8b-instant` via `Groq` (keep — document the local-vs-hosted trade-off explicitly instead of silently diverging from "Gemma via Ollama") |
| 9. Score | Faithfulness/confidence, computed and **gated** — if below threshold, respond "not in our database" instead of guessing | LLM-judge call (keep, but act on the score) |
| 10. Persist | Save turn to chat history | `MongoDB` (motor) |
| 11. Display | Show the answer **and** which source chunk(s) backed it, plus the confidence score | Next.js — new work, data already exists in the API response |
